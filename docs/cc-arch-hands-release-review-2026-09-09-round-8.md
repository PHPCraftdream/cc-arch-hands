## P2-1 — Старый refresh публикует после смены владельца

**Где:** `lib/update-check.js:220`, публикация из `getLatestVersion()`.

Refresh удерживал lease, но не передавал проверку владения в atomic writer.
Вследствие этого A мог продолжить публикацию после takeover другим владельцем B.

Дополнительно новая защита от будущего checkedAt взаимодействовала со старым
nowMs вызова A: после достаточно долгой приостановки A свежая запись B выглядела
для него «будущей» и переставала защищаться веткой changedToFresher.
Одного сравнения timestamps недостаточно для определения полномочий writer.

**Воспроизведение:** используются реальные filesystem и API. В контролируемой
последовательности lease A состаривается через его owner record, B получает
другое поколение и публикует `0.8.2` с более поздним checkedAt. Возобновившийся A
публиковал `0.8.1` и возвращал старую версию. В отдельном сценарии B только
захватывает lease на последней файловой границе A; даже без новой записи B
устаревший A создавал cache внутри чужой критической секции.

**Исправление:** в atomic publication передаются
`assertOwnership: () => renewLease(lock)` и `lifecycleLease: lock`.
Проверка выполняется и внутри файловой операции. Потерявший поколение writer
не публикует; существующий fail-silent путь перечитывает результат преемника.

**Проверка:** два теста в `test/update-refresh-lease.test.js` проверяют конечную
версию, checkedAt, отсутствие недопустимой публикации и сохранение lease B.
Оба падали до изменения и проходят после него. Проверено также в установленном
из tarball runtime. Приоритет P2: повреждался восстановимый update-cache,
не пользовательский settings.json.

## P2-2 — Context sidecar теряет принадлежность своему cache-path

**Где:** `lib/transcript-stats.js:371`, `:374`, `:503`.

`rateLimitsContextPath(cachePath, sessionId)` использовал только dirname(cachePath)
и hash(sessionId). Два разных cache-файла в одной директории поэтому получали
один sidecar для одинакового sessionId. Запись второго меняла contextWindowSize,
который читал первый; maintenance второго мог удалить sidecar первого.

**Воспроизведение:** `rate-limits.json` сохраняет контекст 1 000 000,
`other-cache.json` — 200 000 для того же sessionId. Чтение первого возвращало
200 000. Отдельный тест подтверждает удаление его aged sidecar maintenance-вызовом
для другого cache-path.

**Исправление:** namespace теперь учитывает имя cache-файла. Путь по умолчанию
`rate-limits.json → rate-context/` сохранён. Для custom cache используется
отдельный namespace с SHA-256 имени; read/write/prune применяют одну функцию.
При чтении custom cache не подхватывается неоднозначное содержимое прежнего
общего namespace. Однозначные старые файлы вида
`<cachePath>.context-<sessionHash>.json` продолжают мигрировать.

**Проверка:** `test/rate-cache-isolation.test.js` проверяет независимость чтения,
отсутствие перекрёстного pruning и совместимость custom legacy migration.
Default namespace и существующие bounded-maintenance tests также проходят.

## P2-3 — Миграция выбирает timestamp до проверки пригодности данных

**Где:** `lib/transcript-stats.js:461` и `:466`.

Reader уже отвергал далёкие будущие timestamps, однако migration сравнивала
legacy/current только по capturedAt. Legacy-запись с будущей датой либо
невалидным contextWindowSize могла заменить действующий sidecar. Последующее
чтение отвергало новый результат и теряло доступную статистику.

Обратный случай тоже работал неверно: пригодная legacy-запись считалась старее
непригодной будущей current-записи и удалялась без восстановления usable context.

**Исправление:** общий predicate проверяет конечную допустимую дату, freshness
и contextWindowSize до выбора победителя миграции и до выбора read candidate.
Непригодный legacy сохраняется без публикации поверх действующего current;
пригодный legacy может заменить непригодный current с прежним destination CAS.

**Проверка:** три отрицательных сценария в
`test/rate-cache-isolation.test.js` — будущий legacy, невалидный размер в legacy
и будущий current при пригодном legacy. Проверяются возвращённый размер,
точные bytes текущего sidecar и сохранность непригодного legacy.
Существующие сценарии миграции более новой корректной записи не сломаны.

## P3-1 — Повреждённый probe-log приводит к ложной ошибке после успешного stop

**Где:** `lib/probe.js:682`, `lib/cli.js:828`.

`readProbeLog()` включал в records любой распарсенный JSON, в том числе null,
числа, массивы и объекты без строкового raw. При null в последней строке
`probe stop` сначала успешно восстанавливал statusLine и удалял backup, затем
завершался с exit 1 и `Cannot read properties of null (reading 'raw')`.
Для других несхемных records счётчик был неверным. Валидные JSON envelopes
`false` и `null` не отображались из-за проверки truthiness.

**Исправление:** reader пропускает записи, не являющиеся объектом со строковым
raw. CLI различает успешный JSON.parse и truthiness распарсенного значения,
поэтому корректно отображает также false/null.

**Проверка:** четыре теста в `test/probe-log-records.test.js` проверяют reader
и настоящий CLI stop, exit code, восстановленный statusLine, удаление backup,
счётчик и вывод falsy envelopes. До исправления ошибочный stop воспроизводился.
Приоритет P3: проблема затрагивала диагностику повреждённого probe-log после
восстановления settings, а не саму сохранность оригинального statusLine.
