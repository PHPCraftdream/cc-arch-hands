## P1-1 — Недоступная метаинформация считается отсутствием файла и разрешает create-if-missing overwrite

**Где:** `lib/fs-atomic-identity.js:43`, особенно обработка `EPERM`;
`lib/fs-atomic-publication.js:43` и `:145`. Регрессия связана с `d0592ad`.

`regularFileIdentity()` теперь возвращает `null` не только для `ENOENT`,
но и для `EPERM`. Локальный `lstatMaybe()` publication-модуля делает то же.
Для ожидания `exists: false` функция `expectedDestinationMatches()` требует
ровно два таких `null`, поэтому невозможность проверить существующий путь
превращается в разрешение заменить его.

**Воспроизведение в отдельном Node-процессе:** заранее создан файл с содержимым
`FOREIGN ORIGINAL`. Вызван публичный writer с явно заданными mode и условием:

```js
writeFileAtomic(path, 'NEW PAYLOAD', {
  mode: 0o600,
  expectedDestination: { exists: false },
});
```

Через `syncBuiltinESMExports()` инъецирован `EPERM` только для `lstat` этого
конкретного destination. Запись и rename оставались обычными файловыми операциями.
В transient-варианте отказ метаданных прекращался сразу после canonical rename.

| Условие | Результат вызова | Конечные bytes |
|---|---|---|
| Контроль, `lstat` доступен | Отказ из-за существующего destination | `FOREIGN ORIGINAL` |
| `lstat` недоступен до конца операции | `ERR_ATOMIC_RECOVERY_REQUIRED` после commit | `NEW PAYLOAD` |
| `lstat` снова доступен после rename | **Успех** | **`NEW PAYLOAD`** |

Таким образом, нарушено именно условие create-if-missing. Поздняя ошибка
также не спасает исходные bytes. Явный `mode` указан в воспроизведении:
без него ранний запрос existing mode может остановить вызов раньше. Условие
`exists: false` должно сохранять смысл и при переданном mode, как у обычных
installer-вызовов.

Это проверка логики при отказе чтения метаданных, а не утверждение, что любой
Windows `EPERM` обязательно допускает rename. Опасное условие — метаданные
недоступны, но запись directory entry разрешена — нельзя считать доказанным
отсутствием файла.

**Что исправить:** различать отсутствие и неопределённый результат inspection.
При `EPERM` допустим ограниченный повтор либо контролируемый отказ, сохраняющий
destination. Только подтверждённый `ENOENT` может удовлетворять create-if-missing.
Перепроверить остальные потребители изменённых identity helpers.

**Критерий закрытия:** оба fault-варианта сохраняют исходный файл; операция
с отсутствующим destination по-прежнему успешно создаёт его. Нельзя исправлять
тест только проверкой кода ошибки: необходимо проверять конечные bytes.

## P1-2 — Смена поколения внутри rollback probe оставляет активный probe без backup

**Где:** `lib/probe.js:76`, `:379`, `:536`, `:634`.

Новые `assertProbeLeaseHeld()` и проверки в catch выполняются перед стадиями.
Но `writeJsonAtomic()` и `rollbackExactPublication()` не получают lease assertion
для своих внутренних публикаций/удалений. После первоначальной проверки A
может потерять поколение уже внутри rollback, а затем продолжить cleanup backup.

**Воспроизведение реальными API с двумя операциями и worker-потоком:**

1. A включает probe. На `enable-post-settings-rename` инъецируется ошибка,
   чтобы вызвать штатный rollback.
2. В `probe-rollback-before-final` timestamp владельца A в fixture состарен
   на час. Это заменяет ожидание expiry; системное время не менялось.
3. B получает новое поколение того же lock и вызывает `disableProbe()`.
   После восстановления исходной statusLine B приостановлен до проверки backup.
4. A продолжает откат. Его settings CAS уже не проходит, но дальнейший cleanup
   удаляет backup, который B ещё использует.
5. B видит `BackupChangedError` и откатывает своё восстановление settings,
   возвращая включённый probe. Backup уже отсутствует.

Получено:

```text
после A: исходная statusLine, backup отсутствует
B: BackupChangedError
конечная statusLine.cah-name = probe
конечный backup отсутствует
повтор disableProbe() -> MissingBackupError
```

Использованы штатные test boundaries и кооперативные `Atomics.wait/notify`
для порядка операций. Worker выполнял настоящий `disableProbe()`; его
поколение lock отличалось от поколения A.

**Что исправить:** передавать проверку исходного lease generation в каждый
низкоуровневый writer/remover, включая rollback, и повторять её после внутренних
ожиданий. После потери поколения A не должен удалять backup B. Дополнительно
проверить инвариант отката stop: возврат к активному probe допустим только
при сохранённом пригодном backup.

**Критерий закрытия:** в данном чередовании более новая операция завершается
с исходной пользовательской настройкой либо сохраняется активный probe с
пригодным backup. Состояние «probe активен, backup отсутствует» недопустимо.

## P2-1 — Общий settings-lock использует несовместимые namespace для временных fence

**Где:** `lib/settings-lock.js:89` и `lib/probe.js:261`.

Settings helper по умолчанию использует `.stale.`, а probe передаёт `.stale-`.
Это влияет на `hasInFlightFence()`: каждый участник видит только свой шаблон
имён. Во время heartbeat renewal канонический lock временно перемещается в
fence; другой участник не замечает этот действующий fence и получает lock.

**Воспроизведение:** A получил shared settings-lock. Его heartbeat в fixture
состарен на три минуты, оставаясь внутри пятиминутной lease, чтобы вызвать
настоящее `renewLease()`. В фазе `lease-renew/vacancy` вызван реальный
`enableProbe()`.

```text
A fence suffix = .stale.
probe успешно изменил settings внутри renewal A
renewLease(A) = true
settingsLockOwned(A) = true
```

Контроль с одинаковым `.stale-` для обоих участников:

```text
probe -> ProbeBusyError
renewLease(A) = true
settingsLockOwned(A) = true
settings остаётся неизменённым
```

Здесь подтверждён вход другого writer в защищённую секцию; последующий
bytes-check одного из mutator-ов может обнаружить конфликт, но mutex уже
не выполняет обещанную сериализацию.

**Что исправить:** единая политика fence namespace для всех участников
одного settings-lock, включая acquire, renew, release и recovery. Если нужна
миграция старого формата, её нужно обработать явно, сохраняя видимость всех
действующих поколений. Одного совпадения канонического `.lock` недостаточно.

## P3-1 — Новые инструкции навыков называют несуществующие команды probe

**Где:** `templates/skills/clock/SKILL.md:266` и
`templates/skills/checkpoint-watch/SKILL.md:151`.

Текст ссылается на `cah probe --enable/--disable`. Реальный CLI поддерживает
`cah probe statusline start` и `cah probe statusline stop`.
Запуск `cah probe --enable` отклоняется: `unknown target "--enable"`.

Исправить примеры на существующие команды. Это неблокирующая правка документации.

## Порядок дальнейшей работы

Сначала закрыть оба P1 с проверкой конечного содержимого файлов, затем
согласовать fence namespace и обновить команды в инструкциях. После изменений
повторить регрессии и полный набор на одной закреплённой ревизии, а также
установку и probe round-trip из финального tarball.

Основной недостаток текущих исправлений — проверки до операции не всегда
сохраняют своё значение внутри неё: неизвестное состояние превращается в
отсутствие, а действующее поколение проверяется раньше последней мутации.
Зелёные штатные тесты эти два перехода пока не контролируют.

Продуктовый код, версии и CI этим отчётом не изменяются. Публикация и push
не выполнялись.
