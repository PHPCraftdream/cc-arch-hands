# Релизное ревью cc-arch-hands — 2026-09-08

## Вердикт

**Текущий HEAD не готов к релизу.** Подтверждены два P1: регрессия очистки
публикации живого процесса и потеря резервной копии пользовательской настройки
при неудачном включении probe. Первый дефект воспроизводится существующими
тестами, второй — отдельной изолированной инъекцией ошибки после rename.

Итого: **P0 — 0, P1 — 2, P2 — 3, P3 — 1.** Отсутствие найденных P0 не означает
доказанного отсутствия всех возможных дефектов.

- Дополнительные воспроизведения, архив npm и установки находились во временных
  каталогах вне репозитория, с изолированными `HOME` и `USERPROFILE` для запускаемых утилит.

## P1-1 — Очистка удаляет fence ещё живого publisher после одной секунды

**Где:** `lib/fs-atomic-publication.js:689`, `lib/fs-atomic.js:757`;
регрессии `test/binstall.test.js:296` и `test/binstall.test.js:317`.
Изменение maintenance-ветки внесено в `678c88c`; аналогичное ограничение
acquirer-ветки появилось в `301b124`.

После успешного canonical rename `recoverOccupiedFence()` защищает committed
fence только пока `!fenceIsStale(...)`. `FENCE_STALE_MS` равен 1000. В maintenance
ветке живой PID больше не удерживает защиту после истечения этого срока.

Но возраст proof — не доказательство завершения процесса или утраты его
права завершить операцию. Обычная приостановка процесса, медленная файловая
система или задержка между rename и cleanup выводят живого publisher за это окно.
Параллельный `writeBins()` удаляет его proof/fence, после чего publisher получает
`ERR_ATOMIC_RECOVERY_REQUIRED` вместо успеха. В end-to-end сценарии `cah-stamp`
завершается без ожидаемого `systemMessage`.

**Воспроизведение на неизменённом HEAD:**

```sh
node --test --test-name-pattern="paused after the canonical rename|cah-stamp child paused after the rename" test/binstall.test.js
```

Оба теста упали и в полном прогоне, и отдельно. Первый: exit 3 вместо 0,
`FAILED:ERR_ATOMIC_RECOVERY_REQUIRED`. Второй: `stdout=""`, строка stamp отсутствует.
Это не вывод только из теоретического TOCTOU и не результат искусственной нагрузки.

**Что исправить:** разделить борьбу с повторным использованием PID и право
живого publisher завершить уже committed операцию. Нужна проверяемая идентичность
владельца/поколения либо корректное, учитывающее транзакцию завершение после чужой
очистки. Простое увеличение 1000 мс лишь сдвинет дефект; вечная вера одному PID
вернёт прежнюю проблему восстановления.

**Критерий закрытия:** оба существующих теста зелёные; добавить управляемую
приостановку дольше freshness window и проверить одновременно завершение
живого publisher, сохранность successor и восстановление после реально умершего
владельца, включая случай повторного использования PID.

## P1-2 — Ошибка после публикации settings оставляет probe включённым без backup

**Где:** `lib/probe.js:407`, `lib/probe.js:426`, `lib/probe.js:315`;
контракт ошибки — `lib/fs-atomic.js:183`.

`publishedSettingsSnapshot` присваивается только после возврата
`writeJsonAtomic()`. Если `writeFileAtomic()` уже переименовал временный файл
в `settings.json`, но последующая синхронизация/проверка завершилась ошибкой,
переменная остаётся `null`. При этом ошибка содержит `committedPublication`.

`enableProbe()` эту информацию не использует: откат settings с `null` ничего
не делает, затем откат backup удаляет только что созданную резервную копию.
В результате новая probe-настройка остаётся канонической, а исходная
пользовательская `statusLine` больше не доступна через предусмотренный механизм восстановления.

**Изолированное воспроизведение:** существующий settings с
`statusLine.command = "original-user-command"`; backup изначально отсутствует.
Через штатный `testInterlock` выброшена ошибка на третьей фазе
`write-after-rename-before-sync`: сначала публикуется log, затем backup, затем settings.

```text
enableProbe: injected post-rename settings failure
error.committedPublication: present
settings.statusLine.cah-name: probe
backup exists: false
disableProbe: MissingBackupError
```

Инъекция моделирует ошибку после commit point; в продукте этот участок содержит
реальные fallible операции синхронизации и проверки. Изменялись только временные fixture-файлы.

**Что исправить:** учитывать committed metadata именно соответствующего пути
при ошибке публикации backup/settings; не удалять последнюю пригодную резервную
копию, пока не подтверждено восстановление settings. Применять точную проверку
идентичности, чтобы не откатить чужой successor. Проверить симметричный error path
в `disableProbe()`, а не ограничиваться успешными переходами.

**Критерий закрытия:** тесты ошибок после rename, sync и destination inspection
для обеих частей перехода. После любой ошибки должно оставаться либо исходное
settings, либо включённый probe с пригодным backup; исходная настройка не теряется.

## P2-1 — Путь probe интерпретируется оболочкой как код

**Где:** `lib/probe.js:141` — `buildProbeEntry()`. Старый дефект общего состояния
репозитория, не новая регрессия коммитов сентября.

Код экранирует только двойную кавычку и помещает путь внутрь двойных кавычек:
`node "..."`. В POSIX shell/Git Bash внутри них остаются активны `$variable`,
`$(command)` и обратные кавычки. Поэтому допустимые символы имени каталога
меняют смысл команды; защита от выхода из кавычек не решает эту проблему.

**Воспроизведение:** fixture с буквальным сегментом пути `$(echo CAH_EXPANDED)`.
Прямой запуск Node с массивом аргументов: exit 0, `PROBE_OK`. Запуск сгенерированной
statusLine-команды через Git Bash: exit 1, `MODULE_NOT_FOUND`; оболочка заменила
сегмент на `CAH_EXPANDED`. Для доказательства использовался только безвредный `echo`.

**Что исправить:** формировать литеральный аргумент по правилам реально
используемой оболочки, либо отклонять неподдерживаемые пути явно. Добавить тесты
для пробелов, `$`, backtick и кавычек на поддерживаемых платформах.
Не выдавать это за удалённую уязвимость без модели контроля пути: подтверждены
интерпретация содержимого пути оболочкой и поломка запуска.

## P2-2 — Prerelease-пользователь не получает уведомление о стабильном обновлении

**Где:** `lib/update-check.js:95`; поддержка prerelease-публикации —
`.github/workflows/publish.yml:45`.

`isNewerVersion()` разбивает строки по точкам и применяет `Number`. Часть
`0-rc` становится `NaN`, и функция возвращает `false` ещё до сравнения версий:

```js
isNewerVersion('0.8.0-rc.1', '0.8.0') // false, должно быть true
isNewerVersion('0.8.0-rc.1', '0.9.0') // false, должно быть true
```

Оба результата получены прямым вызовом функции. При этом publish workflow явно
разрешает prerelease и публикует его с тегом `next`. Такой пользователь остаётся
без штатного уведомления при появлении stable. Для текущего stable `0.8.0`
обычные числовые сравнения работают; это не самостоятельный блокер stable-релиза.

**Что исправить:** сравнивать SemVer, отделяя prerelease и build metadata, либо
согласованно убрать неподдерживаемый prerelease-сценарий. Добавить проверки
`rc -> stable`, `rc.2 -> rc.10`, следующего minor и build metadata.
Правила: [SemVer 2.0.0, precedence](https://semver.org/#spec-item-11).

## P2-3 — Публикация не зависит от полной матрицы поддерживаемых сред

**Где:** `.github/workflows/ci.yml:15`, `.github/workflows/publish.yml:9`
и `.github/workflows/publish.yml:18`.

Обычный CI проверяет три ОС на Node 18.19.0/20/22, но не Node 24. Release workflow
запускает собственный `test` только на Ubuntu/Node 22 и зависит именно от него,
а не от полной матрицы на публикуемом теге. Из кода workflow не следует, что
ошибка на Windows/macOS или Node 24 остановит публикацию.

На дату проверки Node 24 и 22 — LTS, 18 и 20 — EOL.
Источник: [официальная таблица выпусков Node.js](https://nodejs.org/en/about/previous-releases).
Заявленный `engines >=18.19.0` допускает Node 24; локальный полный прогон выше
как раз выполнен на этой версии и не зелёный. Проверка старого minimum полезна,
но не заменяет проверку актуальной LTS.

**Что улучшить перед выпуском:** переиспользовать одну матрицу проверки для CI
и release/tag; включить Node 24, сохранить минимальную поддерживаемую версию,
добавить smoke из созданного tarball до publish. Решение о прекращении поддержки
старых Node принимать отдельно: само по себе это замечание не требует повышения
`engines` или версии проекта. Внешние branch-protection правила здесь не проверены.

## P3-1 — CONTRIBUTING направляет новый companion bin по устаревшему пути

**Где:** `CONTRIBUTING.md:31`, особенно `:36` и `:37`;
актуальные контракты — `lib/binstall/runtime.js:11` и `test/discovery-contract.test.js:65`.

Инструкция предлагает добавить тестовый файл в `package.json` test script,
хотя контракт требует ровно `node --test --test-concurrency=1` с автоматическим
discovery. Следование этой инструкции ломает контрактный тест.

В той же инструкции отсутствует регистрация runtime leaf и новых зависимостей
в `BinFileDefinitions`. Одного npm `bin` недостаточно, чтобы файл попал в
копируемое дерево `cah-bin`, на которое ссылаются hooks.

**Что улучшить:** описать registry + dependency closure + тест установленного
артефакта, а для тестов — создание `test/*.test.js` без ручного списка в scripts.
Это небольшая документационная правка, не блокер текущего релиза.

## Оценка направления изменений и порядок действий

За период заметно усилены точные проверки идентичности файлов, замороженное
поколение исходников runtime, восстановление после аварии, ограниченные обходы
каталогов и жизненный цикл тестовых процессов. Пакет не приобрёл runtime-зависимостей;
version guard и отдельный npm dist-tag для prerelease присутствуют. Используемые
версии Actions v7 существуют: [checkout](https://github.com/actions/checkout/releases/tag/v7.0.0),
[setup-node](https://github.com/actions/setup-node/releases/tag/v7.0.0).

Главная системная проблема сейчас — согласованность контрактов между слоями:
исправление восстановления PID ослабило гарантию живого publisher, а новый
контракт committed error был учтён установщиком, но не probe. Следующие изменения
стоит проверять по всем потребителям общего примитива, а не только локальным regression tests.

Порядок до релиза:

1. Закрыть P1-1 и P1-2 с указанными регрессиями, не ослабляя существующие assertions.
2. Получить зелёный полный прогон на публикуемом состоянии и целевых ОС/Node;
   воспроизводимые падения не считать допустимыми flaky-тестами.
3. Закрыть shell-quoting P2-1 и усилить release gate P2-3. Для prerelease обязательно
   закрыть P2-2; для stable явно зафиксировать, если он остаётся известным ограничением.
4. Обновить CONTRIBUTING и пользовательские release notes по фактически вошедшим
   изменениям, повторить установку/обновление/удаление из финального tarball.
5. Только затем создавать релиз. Этот отчёт не изменяет версии, не публикует пакет
   и не заменяет решение владельца репозитория о выпуске.
