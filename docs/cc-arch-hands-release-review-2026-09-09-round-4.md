# Релизное ревью cc-arch-hands — раунд 4, 2026-09-09

## Вердикт

**Выпуск пока не рекомендую.** Новый settings-lock устраняет обычную гонку
двух писателей, но его правила reclaim/release допускают удаление чужих данных
и потерю взаимного исключения. Отдельно подтверждены несогласованные lock-и
навыков и probe, а также необработанный transient `EPERM` в atomic publication.

Итого: **P0 — 0, P1 — 1, P2 — 2, P3 — 1.** P1 объединяет связанные дефекты
одного lifecycle-протокола, а не выдаёт каждый его error path за отдельный блокер.

CI остаётся за рамками замечаний по ранее полученному уточнению пользователя.
Локальные тесты и ошибки продуктового кода проверялись; конфигурация и лечение
CI здесь не оцениваются.

## Что исправлено после предыдущего раунда

- В навыках появился общий lock на весь read-modify-write цикл. Тест обычного
  конкурирующего сохранения теперь проходит, включая контроль без lock.
- Renew/reclaim используют согласованное правило expiry; добавлен допуск
  небольшого рассогласования времени, чтобы не считать свежего владельца истёкшим
  только из-за задержки между захватом времени и проверкой.
- Doctor/list используют ту же структурную классификацию runtime leaf, что и
  install preflight. Матрица plain/foreign/directory/symlink/hardlink проходит.

Эти исправления не отменяют найденные ниже проблемы lifecycle нового lock
и взаимодействия нескольких путей изменения settings.

## P1-1 — Новый settings-lock небезопасен при инициализации, reclaim и release

**Где:** `templates/skills/clock/SKILL.md:272` и `:290`,
`templates/skills/checkpoint-watch/SKILL.md:157` и `:175`;
исполняемая модель — `test/skill-settings-contract.test.js:59`, `:84`.

Протокол объявляет lock брошенным сразу, если `owner.json` отсутствует или
нечитаем. Он переименовывает такой lock и удаляет переименованную копию.
На release предписано удалять канонический `settings.json.lock` в любом исходе,
без проверки, что он всё ещё принадлежит этой операции. В owner записываются
только PID и timestamp; продление heartbeat и проверка поколения перед
публикацией/release не предусмотрены.

### Наблюдение A: свежая reservation и чужие данные удаляются

Из текущего контрактного теста извлечена и выполнена **его собственная**
`documentedAtomicSave()` без изменения алгоритма.

- Fixture 1: только что созданный пустой `settings.json.lock`, ещё без owner.
- Fixture 2: такой же свежий каталог с независимым `user-recovery.txt`, без owner.

В обоих случаях save сообщает `{ published: true, conflict: false }`, а
исходный каталог удалён. Во втором случае вместе с ним удалены recovery-данные;
после операции в fixture остался только `settings.json`.

Отсутствие owner-файла не доказывает abandonment: существует нормальный
промежуток между успешным `mkdir` и записью owner. Ошибка чтения также не
является доказательством владения чужим каталогом или права удалить его содержимое.

### Наблюдение B: два процесса получают доступ через initialization gap

В двухпроцессной модели опубликованных lock-шагов:

```text
A: mkdir(settings.json.lock), остановка до записи owner
B: owner отсутствует -> reclaim; создаёт новый lock и записывает owner B
A: продолжает и записывает owner A в канонический путь, уже занятый B

B acquired during A initialization = true
A overwrote B owner = true
```

Процессы синхронизированы IPC; дополнительных вычислительных нагрузок нет.
Именно новый «общий» lock снова допускает двух считающих себя владельцами
писателей в одной критической секции.

### Наблюдение C: старый владелец удаляет lock живого преемника

Ещё один двухпроцессный сценарий: A получил lock; его timestamp в fixture
состарен на час вместо реального ожидания; B штатно выполнил reclaim и получил
свежий lock. Затем A завершает свою операцию и исполняет предписанный release.

```text
B owns canonical lock before A release = true
B process still alive = true
successor lock survived A release = false
```

Старый finally удаляет owner-файл и каталог B. После этого третья операция
может войти, пока B ещё работает. Проверка bytes settings не восстанавливает
утраченное взаимное исключение.

**Что исправить:** не развивать ещё одну упрощённую копию lease-протокола
только в prose. Нужен общий исполняемый settings mutator с проверкой поколения
владельца, безопасным временем ожидания ownerless reservation, консервативным
поведением при unreadable/foreign state и release только своего lock.
Утративший lease writer не должен публиковать результат или удалять successor.
Можно переиспользовать проверенные примитивы проекта вместо ручной рекурсивной
очистки любого занятого имени.

**Критерий закрытия:** регрессии на fresh ownerless lock, unreadable owner,
постороннее содержимое, pause/reclaim/resume и release старого владельца.
Данные сохраняются, одновременно допущен максимум один владелец, а устаревшая
операция явно отказывается от commit/release чужого поколения.

Это замечание к поставляемому протоколу и его исполняемым моделям, не заявление
о запуске навыка в живой LLM-сессии.

## P2-1 — Skills и probe используют разные lock-и для одного settings.json

**Где:** оба шаблона предписывают `settings.json.lock`;
`lib/probe.js:30` и `:260` используют `settings.json.probe-lock`.

Даже после исправления lifecycle из P1 эти mutex-имена не сериализуют
собственные settings writers одного пакета. CLI probe может полностью завершить
свою запись, пока `/clock` удерживает другой lock и собирается опубликовать
ранее прочитанный JSON.

**Воспроизведение:** использована модель навыка из текущего теста с одной
дополнительной точкой остановки после финальной bytes-проверки, перед rename.
В этой точке вызван реальный `enableProbe()`. Модель clock только добавляла
PostToolUse hook; сама она не меняла прочитанную statusLine.

```text
skill settings.json.lock held during enableProbe = true
enableProbe returned successfully
skill save -> published=true, conflict=false
final statusLine.cah-name = clock, а не probe
probe backup still exists = true
```

Успешно включённый probe исчез из settings. Воспроизведение задаёт допустимое
чередование операций; тестовая точка представляет приостановку писателя между
проверкой и commit, а не изменение логики проверок.

**Что исправить:** после P1 свести все собственные settings mutators, включая
enable/disable probe и навыки, к одному lock namespace и одному формату владельца.
Одной замены suffix недостаточно, пока протокол навыков остаётся небезопасным.
Проверку независимого редактора, не использующего lock, сохранить как отдельную
ограниченную защиту; она не заменяет общую сериализацию.

**Критерий закрытия:** интеграционный сценарий clock + probe допускает только
последовательные изменения свежего JSON либо явный busy/conflict; два success
не должны молча терять одно из действий.

## P2-2 — Transient EPERM при mkdir publication fence немедленно выходит наружу

**Где:** `lib/fs-atomic-publication.js:796`–`:808`;
наблюдавшийся regression test — `test/fs-atomic.test.js:470`.

`beginFence()` повторяет acquire при `EEXIST`, но для любой другой ошибки
`mkdirSync` сразу делает throw. В полном локальном прогоне один из конкурентных
publishers завершился с exit 7:

```text
RAW:EPERM:EPERM: operation not permitted,
mkdir '<sandbox>/leaf.json.cah-owned-publish'
```

Команда отдельного повторения:

```sh
node --test --test-name-pattern="never surfaces a raw ENOENT" test/fs-atomic.test.js
```

Повтор прошёл. Это показывает intermittent-характер, но не закрытие дефекта.
Чтобы отделить механизм от вероятности гонки, в отдельном Node-процессе
однократно инъецирован `EPERM` **только** на mkdir нужного publication fence;
следующая попытка того же системного вызова уже была бы разрешена.

Получено: первый `writeFileAtomic()` выбрасывает raw `EPERM`, canonical file
не создан; второй обычный вызов без инъекции успешно пишет payload. Внутреннего
retry для единичного transient отказа нет.

**Что исправить:** добавить ограниченный retry для поддерживаемых transient
ошибок создания fence, с общим deadline, повторной проверкой ownership и без
busy-spin. Постоянный запрет доступа должен закончиться понятной ограниченной
ошибкой; нельзя маскировать `EPERM` как доказанное отсутствие чужого пути.

**Критерий закрытия:** one-shot transient mkdir failure переживается тем же
вызовом; постоянный отказ завершается за ограниченное время, не мутируя чужие
fence/данные. Конкурентный regression снова проверяется без ослабления assertions.

## P3-1 — Retry-паузы расходуют CPU вместо ожидания

**Где:** `lib/fs-atomic-publication.js:81`, `:808`;
`test/skill-settings-contract.test.js:71` и `:488`.

Production `sleepSync()` — пустой цикл по `Date.now()`. При длительном
удержании publication fence до 100 acquire-попыток дают порядка 30 секунд
суммарных активных пауз. Новый `rmDirWithRetry()` в двух местах тестовой модели
также повторяет удаление без паузы до двухсекундного deadline.

Это статическое замечание к реализации ожидания, **не результат искусственного
нагрузочного эксперимента** и не измерение процента CPU на машине пользователя.
Такие циклы усиливают конкуренцию с владельцем ресурса, которому самому нужно
получить процессорное время, и затрудняют интерпретацию timing-sensitive тестов.

**Улучшение:** переиспользовать ожидающий backoff, например уже применяемый
в `lease-lock.js` подход с `Atomics.wait`, или асинхронный таймер там, где API
это позволяет. Deadline оставить общим; устранить дублирование retry helper.
Это не самостоятельный блокер выпуска, но полезнее дальнейшего расширения
временных допусков без исправления самого ожидания.

## Готовность и порядок исправлений

Положительный результат: исходные ошибки doctor и clock-skew из раунда 3
закрыты в проверенных сценариях; обычная сериализация двух навыков работает;
пакет собирается и его установленный runtime запускается.

Следующий шаг по продукту:

1. Закрыть весь lifecycle settings-lock и использовать одну реализацию владения.
2. Подключить к ней probe, проверить общие конкурентные переходы.
3. Исправить transient mkdir retry и выполнить новый полный прогон на
   зафиксированной финальной ревизии, затем повторить tarball smoke.
4. Устранить активное ожидание без создания искусственной нагрузки.

Вердикт не основан на состоянии CI: его отдельная работа не включена в этот
раунд. Продуктовые изменения, повышение версий, публикация и push этим отчётом
не выполняются.
