## P1-1 — Append-сборщик probe обходит проверку безопасности log-файла

**Где:** `bin/cah-status-probe.js`, прежний вызов
`writeFileSync(LOG_PATH, record, { flag: 'a' })`; исправление — `appendRecord()`.

`enableProbe()` уже отказывался работать с symlink и multi-hardlink в logPath.
Но эта проверка выполнялась только при включении. Сам запускаемый statusLine-bin
каждый раз открывал путь на append без проверки. Если между включением и следующим
вызовом logPath становился ссылкой на пользовательский JSON, новая запись
попадала в этот JSON и делала его непригодным для обычного JSON.parse.
Это старый дефект сборщика, а не регрессия последнего `7612a24`.

**Подтверждение:** реальный дочерний Node-процесс, обычные файловые операции.
Для hardlink и symlink файл с `{"userSetting":"keep"}` получал дополнительный
JSONL-record. Dangling symlink приводил к созданию отсутствующего target.
До исправления все три отрицательных сценария воспроизводились.

**Исправление:** проверяются тип и число ссылок; отсутствующий log создаётся
эксклюзивно. После открытия повторно проверяются descriptor и directory entry:
regular file, одна ссылка, совпадающие BigInt dev/ino, соответствие исходной
идентичности. Запись идёт через проверенный fd; fd закрывается в finally.
Где доступны, используются O_NOFOLLOW и O_NONBLOCK.
Назначение этих флагов сверено с
[документацией Node.js](https://nodejs.org/api/fs.html#file-open-constants).

**Проверка закрытия:** `test/probe-log.test.js` — обычное создание и append,
hardlink, обычный/dangling symlink, directory, появление ссылки непосредственно
при open для существующего и отсутствующего log. Проверяются конечные bytes
пользовательского файла, а не только exit code. Отдельно проверен установленный
из tarball сборщик.

Ограничение остаётся прежним для path-based Node API: это не защита от
произвольной подмены предков или создания hardlink злоумышленником с тем же UID
после последней проверки.

## P1-2 — Локальные CLI-тесты меняют глобальные bins пользователя

**Где:** `test/cli.test.js`, subset install/reinstall и часть template-preflight
сценариев; `--cwd` использовался без переназначения HOME/USERPROFILE.

Установка навыков автоматически добавляет зависимость `bins`.
По контракту bins всегда находятся в глобальном `~/.claude/cah-bin/`,
независимо от `--cwd`. Поэтому временный project directory не изолировал эти
тесты: они могли заменить sentinel-owned файлы реальной установки. Зелёный тест
не обнаруживал побочный эффект.

**Подтверждение:** новый внешний harness передаёт CLI-тестам временный
«унаследованный HOME» с заранее записанным owned bin. Исходные тесты заменяли
его содержимое и добавляли runtime-файлы. Harness проверяет, что выбранные
тесты действительно исполнились, а не завершились с нулём без запуска.

**Исправление:** общий beforeEach в CLI-suite создаёт собственный HOME для
каждого теста; cleanup восстанавливает env и удаляет только этот fixture.
Существующие вложенные `withHome()` продолжают работать.

**Проверка закрытия:** `test/cli-isolation.test.js` запускает реальные
subset install/reinstall tests и проверяет неизменность bytes и состава дерева
унаследованной установки. Регрессия до исправления падала, после — проходит.
Повторный полный набор дополнительно запускается с отдельным внешним HOME.

**Операционное примечание:** первый полный прогон исходных тестов действительно
обновил управляемые глобальные bins кодом этого ревью. Это незапланированный
побочный эффект, о котором пользователь уведомлён. Автоматический откат этих
binaries не выполнялся: точный снимок их состояния до теста отсутствует.

## P2-1 — Кэши принимают невозможные будущие даты за свежие

**Где:** `lib/update-check.js:cacheIsFresh`, ветка `changedToFresher`;
`lib/transcript-stats.js:isFresh`.

Проверка только верхней границы возраста принимала отрицательный возраст.
После исправления неверных системных часов кэш мог оставаться «свежим» весь
период до прежней будущей даты. Число `1e400` в JSON давало Infinity и делало
эффект неограниченным: update-check не вызывал fetch, а rate/context-reader
возвращал устаревшие значения.

**Исправление:** timestamp должен быть конечным числом и не превышать now
более чем на существующий пятисекундный допуск scheduling skew.
Проверка применяется и к повторному чтению update-cache перед публикацией,
чтобы concurrent future-dated запись не считалась авторитетным обновлением.

**Проверка закрытия:** `test/cache-time.test.js` проверяет будущую дату,
`1e400`, глобальный rate-cache и context sidecar, восстановление update-cache,
конкурентную будущую запись и допустимое расхождение в одну секунду.
Тесты используют переданный now; системные часы не меняются.

## P2-2 — Одна строка null скрывает статистику последнего ответа

**Где:** `lib/transcript-stats.js:scanTranscriptReverse`, callback `consume`.

JSON `null` успешно проходил JSON.parse, после чего обращение к `obj.type`
бросало исключение. Внешний catch возвращал null для всего транскрипта,
хотя предыдущая строка содержала актуальные model, requestId и usage.
В результате зависимые hook-bin теряли доступную статистику. Это дефект
best-effort обработки некорректного по схеме JSONL, не утверждение, что
обычный Claude Code обязательно пишет такие строки.

**Исправление:** удалена дублирующая небезопасная проверка `obj.type`;
проверка проходит через существующий null-safe `isAssistantEntry()`.
Граница реального assistant turn и запрет смешивания разных requestId сохранены.

**Проверка закрытия:** новая регрессия в
`test-support/transcript-read-cases.js` добавляет после актуального assistant
значения null, false, число, строку и массив; ожидает точные поля нового ответа.
Тот же null-tail проверен на установленном из tarball runtime.

## P2-3 — Тест смены lease зависит от скорости диска и заражает следующий тест

**Где:** `test/binstall.test.js`, три теста expiry/takeover.

Первый полный прогон дал четыре падения с `ERR_BIN_LIFECYCLE_LEASE_LOST`.
Первое — в установке-преемнике, которой тест тоже выставлял lease 2000 ms.
После исключения восстановление env не выполнялось: следующие сценарии
унаследовали `CAH_TEST_ONLY=1` и `CAH_TEST_ONLY_BIN_LEASE_MS=2000` и падали
при обычной подготовке runtime. Отдельный повтор четырёх тестов проходил,
что само по себе не устраняло механизм флейка.

Дополнительно source/destination лежали прямо среди остальных entries системного
TEMP. Это связывало recovery scan с чужими временными файлами и его коротким
временным бюджетом.

**Исправление:** состаривается только owner record остановленного A, после
подтверждённой точки остановки. B получает обычный lease; глобальная настройка
короткого lease больше не меняется. В finally отправляется go и ожидается
завершение A даже при ошибке. Source/destination теперь вложены в собственный
fixture, вместе со служебными sibling-locks; fixture удаляется целиком.

**Проверка закрытия:** три expiry/takeover-сценария и три ранее каскадно
падавших сценария проходят вместе. Assertions сохранения runtime и ошибки
потери lease не ослаблялись. Финальный полный прогон прошёл без падений.

## P2-4 — Медленная подготовка запрещает захват уже свободной блокировки

**Где:** `lib/lease-lock.js:acquireLease`, цикл, ограниченный
`config.recoveryDeadline` ещё до первой попытки mkdir.

Если успешное создание parent directory занимало больше 250 ms, цикл вообще
не выполнялся. Аналогично, успешное удаление истёкшего claim могло исчерпать
бюджет: canonical path уже свободен, но следующего mkdir не происходило.
Вызыватель получал busy/blocked без фактического конкурента. Это дефект
доступности на медленном filesystem или после задержки планировщика.

Второй полный прогон показал пять отказов в bin lifecycle, migration и
marker-recovery. Дополнительные детерминированные проверки воспроизвели
описанный механизм без искусственной CPU-нагрузки и без ожидания медленного I/O:
после успешной файловой операции сдвигается только локальный test clock.

**Исправление:** максимум две попытки создания claim — первая обычная и одна
после reclaim. Бюджеты повторов отдельных файловых операций сохранены.
Вторая неудачная попытка не запускает ещё один цикл reclaim; проверки fence,
owner и generation не обходятся. Удалён также busy-spin из marker-test helper:
синхронные паузы используют общий `sleepSyncWait()`.

**Проверка закрытия:** `test/lease-acquire-budget.test.js` проверяет оба
сценария медленной подготовки и границу двух попыток с сохранением successor.
Все пять ранее падавших сценариев проходят в целевом наборе; ещё 52 проверки
lease/settings/atomic/rollback проходят без отказов.

## P3-1 — Сравнение SemVer округляет числовые идентификаторы

**Где:** `lib/update-check.js:parseSemver` и `comparePrereleaseIdentifiers`.

Number делает `9007199254740992` и `9007199254740993` неразличимыми;
ещё более длинные значения превращаются в Infinity. Новая версия могла быть
пропущена, а сравнение следующих компонентов могло даже объявить более старую
версию новой. Числовое сравнение требует
[SemVer 2.0.0, пункт 11](https://semver.org/#spec-item-11).

**Исправление:** core и числовые prerelease identifiers сравниваются как BigInt.
Строгая грамматика, отказ для ведущих нулей и игнорирование build metadata
сохранены. Версия самого проекта не повышалась.

**Проверка закрытия:** `test/update-check.test.js` — соседние значения выше
2^53, обратный порядок, ошибочное продвижение по minor, prerelease и числа
длиной более 310 цифр. Приоритет низкий: текущая обычная нумерация проекта
в этот крайний случай не попадала.

## Итоговая оценка

По проверенному коду и Windows-пакету блокирующих замечаний после исправлений
не осталось. Выпуск на остальные поддерживаемые платформы требует отдельного
подтверждения их проверок; этот отчёт не заменяет вынесенный за scope CI.

Улучшения, внесённые в этом раунде: проверки конечных bytes при отказе,
изоляция реального HOME в install-тестах, детерминированная смена поколений
вместо таймерных догадок, ограничение acquire числом реальных попыток и smoke
именно упакованного runtime. Их следует сохранять как регрессионные контракты.
