## P1-1 — Замена settings с сохранённым probe уничтожает последнюю пригодную резервную копию

**Где:** `lib/probe.js:488`, `lib/probe.js:498`, `lib/probe.js:500`;
ошибочное ожидание теста — `test/probe.test.js:780` и `:782`.

Новая ветка cleanup считает: если settings-файл больше не совпадает с нашим
published snapshot, backup нашей операции можно откатить. Комментарий объясняет
это тем, что successor якобы не нуждается в этом backup.

Это неверно для обычного редактора settings: он может сохранить уже включённый
probe, добавив лишь соседнюю настройку. Новый inode не означает, что
`statusLine` перестала зависеть от сохранённого оригинала.

**Воспроизведение без инъекции искусственной I/O-ошибки:**

1. Исходный settings содержит `statusLine.command = "original-user-command"`;
   backup отсутствует.
2. В `enable-post-settings-rename` второй writer читает новый JSON, добавляет
   `editorSetting: "preserve me"` и атомарно заменяет файл.
3. Собственная проверка `enableProbe()` обнаруживает смену settings и выбрасывает
   `managed destination leaf changed concurrently; refusing operation`.
4. Откат settings правильно не трогает successor. Но backup удаляется.

Получено:

```text
settings.statusLine.cah-name = probe
settings.editorSetting = preserve me
backup exists = false
disableProbe() -> MissingBackupError
```

Новый тест уже создаёт почти такое же состояние: successor получает те же
probe-байты, а assertion требует отсутствия backup. Поэтому зелёный тест здесь
закрепляет небезопасный результат вместо восстановления инварианта.

**Исправление:** различать владение целым файлом и потребность актуальной
`statusLine` в backup. Если откат settings не подтверждён, нельзя удалять
единственную копию оригинала, пока не доказано, что действующий probe больше
её не использует. При невозможности безопасно прочитать successor выбирать
сохранение recovery data, не удаление. Чужие изменения settings не откатывать.

**Критерий закрытия:** новый regression с обычным редакторским сохранением,
а также с byte-identical replacement; последующий `disableProbe()` должен
восстановить исходную statusLine, сохранив независимую настройку редактора.
Изменить неверный oracle существующего successor-теста.

## P1-2 — Навыки clock/checkpoint-watch предписывают запись поверх чужого временного файла и устаревшего settings

**Где:** `templates/skills/clock/SKILL.md:183`, `:244`;
`templates/skills/checkpoint-watch/SKILL.md:126`.

Оба поставляемых навыка до сих пор требуют: stringify, записать в фиксированный
`settings.json.tmp`, затем rename поверх `settings.json`. Не указаны эксклюзивное
создание временного файла, проверка его владения и проверка, что исходный
settings не изменился после чтения. Защита, добавленная в библиотечный atomic
writer, здесь не применяется: навыки дают агенту отдельный алгоритм.

**Проверка буквального алгоритма в fixture:** заранее созданы settings и
`settings.json.tmp` с независимыми recovery-данными. После чтения settings другой
writer добавил `independentlyAdded: "must survive"`. Затем выполнены предписанные
запись фиксированного tmp и rename.

Результат: прежние tmp-данные потеряны; tmp-путь исчез; независимо добавленная
настройка отсутствует в конечном JSON. Даже без второго writer перезапись
предсуществующего tmp уже теряет чужие данные.

Это дефект **опубликованной инструкции**, а не утверждение, что в этом ревью
запускалась живая LLM и гарантированно выбрала конкретный файловый API.
Строгое следование инструкции воспроизводит потерю данных. Atomic rename
защищает от частично записанного файла, но не делает read-modify-write транзакцией.

**Исправление:** дать навыкам общий безопасный settings mutator либо явно
задать протокол уникального эксклюзивного temp, проверки ожидаемого settings
перед публикацией и повторного merge/отказа при конфликте. Не удалять и не
перезаписывать заранее существующий `settings.json.tmp`.

**Критерий закрытия:** исполняемые контрактные тесты опубликованного алгоритма:
чужой tmp сохраняется, конкурентная настройка сохраняется либо операция явно
отказывается от публикации, а clock и checkpoint-watch не стирают hooks друг друга.

## P2-1 — Persisted lease token/generation снова могут закрепить fence при повторном использовании PID

**Где:** `lib/fs-atomic-publication.js:267`, `:743`;
сравнить проверку срока heartbeat в `renewLease()` в `lib/lease-lock.js`.

`committedLeaseStillHeld()` проверяет совпадение token/generation с owner.json,
но не действительность lease по времени. После аварии owner.json как раз
остаётся с прежними token/generation. Если числовой PID уже принадлежит другому
живому процессу, обе проверки дают «живой владелец + его lease», хотя настоящего
publisher больше нет. Возраст proof больше не ограничивает эту ветку.

Новый тест recycled PID покрывает lease-less publisher; реальные stamp-записи
передают `lifecycleLease` (`bin/cah-stamp.js:248`).

**Воспроизведение:** реальный child получил lease, выполнил canonical rename и
завершился с кодом 77 до cleanup. Затем в fixture смоделировано повторное
использование PID: числовой PID в proof/owner заменён на PID живого родителя,
времена состарены на сутки, token/generation сохранены. Реального принудительного
повторного использования PID операционной системой не выполнялось.

```text
renewLease(expired owner) = false
recoverPublicationFence(...deferCommitted) = false, false, false
fence still exists = true
acquireLease() for a legitimate successor = success
recovery after successor acquisition = true
committed payload unchanged
```

То есть одна подсистема уже отвергает lease как истёкший, другая доверяет ему
без временной границы. Для закрытой сессии, lease которой больше никто не
запрашивает, maintenance не продвигается. Это не утверждение, что любой новый
владелец того же lease блокируется: контрольный takeover как раз разблокировал recovery.

**Исправление:** согласовать доказательство живой lease с её expiry/heartbeat
и идентичностью запуска процесса. Сам факт сохранённого owner.json не является
доказательством жизни прежней транзакции. Сохранить уже добавленное безопасное
завершение действительно живого publisher после чужой cleanup.

**Критерий закрытия:** leased и lease-less варианты death/recycled PID,
истёкший heartbeat и живой медленный owner; maintenance должно сходиться без
обязательного повторного открытия прежней пользовательской сессии.

## P2-2 — Shell-защита исправлена в probe, но отсутствует в основных навыках

**Где:** `templates/skills/clock/SKILL.md:68` и
`templates/skills/checkpoint-watch/SKILL.md:48`.

Навыки по-прежнему требуют просто подставить HOME в double-quoted command:

```text
node "<HOME>/.claude/cah-bin/bin/cah-status.js"
node "<HOME>/.claude/cah-bin/bin/cah-stamp.js"
node "<HOME>/.claude/cah-bin/bin/cah-checkpoint-hint.js"
```

`ProbePathUnsafeError` из `lib/probe.js` этот путь построения команд не защищает.
Double quotes не отключают `$()` и backticks в POSIX shell/Git Bash.

**Воспроизведение:** извлечены три строки из самих templates, `<HOME>` заменён
на fixture-путь с буквальным сегментом `$(echo CAH_EXPANDED)`. Для всех трёх
файлов прямой Node argv-запуск дал exit 0; запуск строки через Git Bash — exit 1,
`MODULE_NOT_FOUND`, с подставленным результатом безвредного `echo`.

**Исправление:** распространить согласованную политику литеральных путей или
явного отказа на все четыре shell entry points и на их миграцию. Добавить
контрактный shell-тест для строк, действительно опубликованных в templates.
Не выдавать доказанную интерпретацию пути за удалённую эксплуатацию без модели
контроля HOME: подтверждены неправильный запуск и выполнение shell substitution.

## P2-3 — clock-тесты читают пользовательский update-cache и зависят от опубликованной версии

**Где:** `test/clock.test.js:16` и `:21`; потребитель —
`bin/cah-status.js:32` и `:128`.

Helper изолирует только `CAH_RATE_LIMITS_CACHE`. Он наследует HOME/USERPROFILE
и не задаёт свой `CAH_UPDATE_CHECK_CACHE`. Status bin при этом читает
`<HOME>/.claude/cah-bin/cache/update-check.json`; при устаревшем или отсутствующем
кеше может вызвать registry fetch и записать его в этот пользовательский путь.

**Контрольный эксперимент без сети и без изменения реального домашнего каталога:**

1. Запустить неизменённый `node --test test/clock.test.js` с отдельными HOME и
   USERPROFILE, содержащими свежий update-cache `latestVersion: "0.8.0"`.
   Результат: 11 passed.
2. Повторить в другой такой же песочнице, но с `latestVersion: "99.0.0"`.
   Результат: 7 passed, 4 failed. В фактическом stdout появился `· 🔵 v99.0.0`,
   который противоречит точным ожиданиям tests.

Это объясняет, почему один зелёный прогон не доказывает воспроизводимость suite:
результат зависит от состояния машины, а со временем — от npm latest. Это также
нарушает ожидание, что тестирование не обновляет runtime-cache реального пользователя.
Для штатного полного прогона здесь не утверждается, что реальный cache был
изменён: отсутствие изоляции установлено по коду, влияние состояния — контролируемым опытом.

**Исправление:** отдельные fixture HOME/USERPROFILE и update-cache с фиксированным
содержимым для каждого соответствующего теста; исключить live-network lookup
из formatter-тестов. Сценарий update suffix проверять отдельно с явными входами.
Не заменять точные assertions на терпящие случайный suffix.

## P3-1 — Новый SemVer parser принимает запрещённые ведущие нули

**Где:** `lib/update-check.js:97` и `:107`.

Обычный prerelease precedence исправлен, но regexp принимает любые `\d+`
в core, а числовые prerelease identifiers не валидируются на ведущий ноль.
Проверено:

```js
isNewerVersion('0.8.0', '00.9.0')             // true
isNewerVersion('0.8.0-rc.1', '0.8.0-rc.02')   // true
```

Обе candidate-строки невалидны по [SemVer, пункт 2](https://semver.org/#spec-item-2)
и [пункт 9](https://semver.org/#spec-item-9). Это противоречит обещанию функции
не показывать ложное обновление для malformed input. Для обычных версий из
нормализованного registry это не блокер выпуска.

**Исправление:** валидировать core как `0|[1-9][0-9]*`, аналогично проверять
numeric prerelease identifiers; добавить негативные tests. Не вводить новую
зависимость или повышать версии ради этой небольшой проверки без отдельного решения.

## Готовность и следующие действия

Положительный результат раунда: исправления первого отчёта действительно
работают в исходных сценариях; пакет собирается, обычный lifecycle работает,
матрица публикации усилена, полный локальный suite зелёный.

Но перенос гарантий между слоями остаётся неполным: владение inode смешивается
с потребностью в backup, существование owner.json — с действительным lease,
а безопасные библиотечные операции сосуществуют с небезопасными инструкциями
для изменения того же settings.json.

Перед релизом:

1. Закрыть оба P1 и исправить неверный successor-test oracle.
2. Закрыть leased recovery и изоляцию clock-тестов, распространить shell-политику
   на устанавливаемые навыки; не ограничиваться повтором прежних happy-path tests.
3. Проверить финальный tag полной настроенной матрицей и повторить tarball smoke.
   Полезно также запускать в самом publish smoke все четыре установленных bin:
   добавленная CLI-проверка install/doctor/list/uninstall их не исполняет.
4. Обновить release notes по реально закрытым ограничениям. P3-1 можно исправить
   отдельно, не подменяя им работу над сохранностью пользовательских настроек.

Этот отчёт не изменяет продуктовый код, существующие тесты и версии, не запускает
публикацию и не является подтверждением работы удалённых CI jobs.
