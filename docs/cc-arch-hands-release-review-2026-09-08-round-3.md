## P1-1 — Проверка перед rename не предотвращает lost update между двумя навыками

**Где:** `templates/skills/clock/SKILL.md:270`,
`templates/skills/checkpoint-watch/SKILL.md:155`;
модель и её граница тестирования — `test/skill-settings-contract.test.js:45`.

Текущий протокол: прочитать settings, подготовить уникальный temp, непосредственно
перед rename повторно сравнить bytes, затем переименовать temp поверх settings.
Между последней проверкой и rename нет общей блокировки для сотрудничающих писателей.
Уникальное имя temp не защищает общую каноническую запись.

Допустимо такое чередование двух независимых процессов:

```text
A: прочитал S0, подготовил S0 + clock
B: прочитал S0, подготовил S0 + checkpoint-watch
A: повторно прочитал S0 -> проверка успешна
B: повторно прочитал S0 -> проверка успешна
A: rename -> опубликован clock, success
B: rename -> опубликован checkpoint-watch, success; clock потерян
```

**Воспроизведение:** два реальных Node-процесса с разными temp-файлами,
созданными эксклюзивно через `wx`. Каждый только добавлял свой hook к
прочитанному массиву, не заменяя его целиком. IPC-барьер задавал указанное
чередование после последней проверки — модель приостановки процесса ОС в
check-to-rename промежутке, без искусственной CPU-нагрузки.

Исходный JSON содержал `foreign-existing`. Получено:

```text
A validated = true; B validated = true
A published = true; B published = true
final hooks = [foreign-existing, checkpoint-watch]
clock отсутствует
```

Результат повторён. Это проверка опубликованного алгоритма, не утверждение
о запуске самого навыка живой LLM. Относительный порядок каждого писателя
соблюдён. Слова «непосредственно перед» не исключают остановку процесса между
двумя отдельными системными вызовами.

Существующий `beforeFinalRename` в контрактном тесте ставит конкурентную запись
**до** повторного чтения. Он подтверждает отказ при уже видимом изменении,
но не проверяет двух писателей, которые оба успели сравнить исходное состояние.

**Что исправить:** сериализовать сотрудничающие clock/checkpoint-watch
read-modify-write операции общим settings-lock или общим mutator, удерживающим
его от чтения до commit. После получения lock перечитать и объединить свежий JSON.
Уникальные temp и проверку внешнего редактирования сохранить.

Это не требование невозможного универсального CAS против любого стороннего
процесса: минимальная обязательная гарантия — не терять изменения между двумя
собственными, следующими одному протоколу навыками. Ограничение относительно
писателей, игнорирующих общий lock, нужно описать отдельно.

**Критерий закрытия:** двухпроцессный regression с обоими writers у commit
boundary; допустимы сохранение обоих hooks или явный конфликт/повтор одного
писателя. Недопустимы два success при потере одного изменения.

## P2-1 — Future-dated lease уже нельзя продлить, но ещё нельзя перехватить

**Где:** `lib/lease-clock.js:23`, `lib/lease-lock.js:543` и `:676`.

Новая общая `leaseExpired()` считает timestamp из будущего истёкшим;
`renewLease()` использует это правило. Но `claimExpired()` осталось отдельным
и разрешает takeover живого PID только при `nowMs >= timestamp`. Таким образом,
одна и та же lease после перевода часов назад получает противоречивые статусы.

**Воспроизведение без изменения системного времени:** lease создана с
переданным `nowMs = t + 1 час`; затем вызовы выполняются с `nowMs = t`, что
моделирует rollback часов после создания lease. Владелец всё ещё жив.

```text
leaseExpired(owner, t) = true
renewLease(owner, t) = false
acquireLease(samePath, { nowMs: t }) = null
```

До освобождения lease прежним владельцем, его смерти либо достижения
будущего timestamp плюс срока lease новый владелец не допускается. Для
приостановленного владельца это может продлить простой гораздо дольше
обычных пяти минут. Это **не** безусловная вечная блокировка: старый владелец
может освободить lease; в диагностике он был корректно освобождён.

**Что исправить:** согласовать правила renew/reclaim/recovery для future,
missing и expired heartbeat, используя общую политику. Если takeover при clock
rollback намеренно запрещён, отдельно определить ограниченное восстановление
и не считать тот же owner одновременно пригодным лишь для блокирования других.

**Критерий закрытия:** общие boundary tests для `t-1`, `t`,
`t + LEASE_MAX_MS` и `t + LEASE_MAX_MS + 1`, с живым и умершим PID;
нормальный действующий owner не перехватывается, clock rollback не оставляет
lease без способного работать владельца на неопределённый для пользователя срок.

## P2-2 — Doctor сообщает healthy для runtime, который install считает foreign

**Где:** `lib/cli.js:523`, `lib/cli.js:575`, `lib/cli.js:626`;
сравнить `lib/binstall.js:273` и `:278`.

`doctor` определяет состояние через чтение содержимого и sentinel. Он не
применяет структурные проверки runtime leaf, которыми руководствуется install:
например, запрет нескольких hardlinks на файл. В результате одно состояние
показывается пользователю одновременно как полностью здоровое и недопустимое.

**Изолированное воспроизведение:**

1. Выполнена нормальная установка в отдельный HOME.
2. Для установленного `lib/lease-clock.js` создан второй hardlink внутри той
   же тестовой песочницы; содержимое файла не менялось, `nlink = 2`.
3. Вызваны штатные CLI-команды:

```text
cah doctor
  exit 0
  mine: 73, legacy: 0, foreign: 0, missing: 0

cah install --only bins
  exit 1
  foreign managed runtime leaf ... multi-hardlink regular file
```

Это не доказательство поломки исполнения именно такого файла: его bytes
остались рабочими. Дефект в health gate и диагностике готовности к безопасному
управлению установкой. `doctor` скрывает уже известный установщику конфликт.

**Что исправить:** переиспользовать read-only часть классификации runtime
preflight в doctor/list, включая тип leaf, symlink и hardlink policy.
Doctor не должен ничего переписывать или устранять самостоятельно.

**Критерий закрытия:** тест соответствия doctor/install для обычного файла,
foreign payload, directory, symlink и multi-hardlink leaf. Для конфликта
выдаётся nonzero и понятный путь, без мутации пользовательских данных.
